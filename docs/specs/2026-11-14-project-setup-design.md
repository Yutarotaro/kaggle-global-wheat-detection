# Global Wheat Detection のプロジェクト構成

## 合意した方針

ローカルMacを開発とデータ分析の拠点とし、Kaggle GPUで本格的な学習を実行する。
GitHubのprivateリポジトリをコード・設定・実験記録の共有先とする。
今回の対象は環境とリポジトリ基盤。モデル実装や学習実行はデータ確認後に行う。

## 構成の比較

| 構成 | 特徴 |
| --- | --- |
| Macですべて実行 | 手軽だがM1・共有メモリ16GBとMPS演算対応が制約になる |
| Kaggle Notebook中心 | GPUを使えるが、ローカルのコード管理との往復が増える |
| ローカル開発＋Kaggle学習（採用） | ローカルで差分管理し、学習はAPI経由で投入できる |

## 管理対象

Git管理するのはPythonコード、実験設定、実行用メタデータ、依存ロック、設計と実験記録。
入力画像、認証情報、重み、生成画像、ログ、予測CSVは管理しない。
リポジトリ内の生成物は`data/`・`models/`・`outputs/`に置く。
重みをGitHubへ保存するためのGit LFSや外部実験管理サービスは、初期段階では導入しない。

## 実行環境

ローカルはPython 3.12とuvで管理し、初期依存は画像・表データの確認と可視化に必要なものに限定する。
Kaggle CLIを依存グループとして追加する。GPU学習依存は後続のモデル選定時に追加する。
GPU実行の可否は実際に選択するモデルで確認し、MPS対応を事前に保証しない。

## データと評価

最初に画像、正解枠、撮影元の分布を確認する。分割はこの調査後に決める。
検証用画像IDは保存して固定し、実験ごとに分割を変えない。
撮影元を跨ぐ性能と類似画像による過大評価に注意する。
コンペの採点ロジックを独立して検証し、標準COCO mAPと区別する。
乱数シードは42、実行時刻はUTCのtz-aware値とする。

## Kaggleへの投入

privateの実行用カーネルにコードと設定を送る。コンペデータはKaggle側で入力として接続する。
認証設定と規約同意、GPU残り枠を確認してから実行する。
認証エラーやGPU割り当て失敗を成功扱いにせず、ステータスと実行ログを確認する。
実行中はチェックポイントを保存し、完了後に成果物をローカルへ取得する。
コードの版、設定、分割、シード、実行環境のバージョンを結果に添える。

## 今回の完了条件

- uvで環境を再現でき、初期依存のimportとKaggle CLIが動く。
- GitHubリポジトリがprivateで、ローカルのoriginがそのリポジトリを指す。
- 生データ・重み・秘密情報がGitの追跡対象外であることを確認する。
- データ取得・学習・認証の未実施状態をREADMEに明記する。
- 必要な検証を終えた作業の区切りで、自分で判断してコミット・pushする。毎回の確認は不要。

## 次の作業候補

まずデータ取得と正解枠の可視化を行う。その後、検証設計と評価処理、
ベースライン学習、Kaggle投入の順に進む。GitHub Issueの作成と分割は別途合意する。
